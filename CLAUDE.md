# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

CarreApp is a Spanish-language PWA that runs the live "Carrera" (a points race between groups) of the Pontificia Universidad Javeriana's induction week. Groups of first-years ("neos", who never use the app) move through campus "bases"; at each base two groups compete in 3 items (barra, pregunta, minijuego), 1 point each. Three roles use the app: **admin** (the coordinator), **base** (inductors who staff a base and score it) and **runner** (corredores who walk with a group). UI text is Spanish; code, comments and identifiers are English. The maintainer talks to Claude in Spanish.

Domain vocabulary: Carrera = edition (`events`), grupo = team, base = base, cruce = match, ronda = round, corredor = runner, inductor = base staff, coordinador = admin, neos = the first-years.

## Commands

```bash
npm run dev                      # Vite, frontend only (http://localhost:5173)
npx vercel dev                   # frontend + the /api/* serverless functions
npm run build                    # tsc -b && vite build (also emits the service worker)
npm run lint                     # oxlint (not ESLint). Only errors matter: the repo has many known
                                 # react(set-state-in-effect) / only-export-components warnings
npx tsc -p api/tsconfig.json     # type-check api/*.ts — `tsc -b` does NOT cover api/ or src/sw.ts
npm test                         # Vitest, ~510 tests, ~20 s (see "Tests" below)
npm run test:race                # the simulated Carrera, verbose narrative
npx vitest run tests/db/rules.test.ts -t "tie"   # one file / one test
npm run check                    # tsc -b + lint + api tsc + tests + build
```

There is no CLI migration tooling: SQL is applied by hand in the Supabase SQL Editor (see Conventions).

**Verifying UI without logging in:** `npm run dev` serves a dev-only `/preview/<screen>` page that renders the real components with sample data (`runner`, `runner-ruta`, `runner-top`, `runner-alertas`, `base`, `base-llegada`, `base-fin`, `base-info`, `admin` = En vivo, `admin-carrera`, `admin-forms`, `map`, `logos` = the logo options gallery, plus `base-resultados`, `dialogs`, `sin-carrera`, `sin-carrera-base`, `runner-sello` = the stamping moment, `sellos` = stamp gallery; the login is just `/login`). Check at 390 px and 1280 px. `src/pages/Preview.tsx` imports components with concrete props, so changing a component's props means updating it too or `tsc -b` breaks. There are no test credentials; never ask for or type the real admin password.

## Architecture

### The database is the rule engine
Business rules live in Postgres (`supabase/migrations/0001…0032`, applied in order; the maintainer applies each by hand and logs it in `Registro-SQL.md`) and are enforced with triggers, constraints and RLS; the client-side checks only exist for UX. Read `docs/wiki/Modelo-de-datos.md` and `Roles-y-permisos.md` before changing behaviour. The rules that shape the code:

- **Scoring:** `match_scores` has one row per (match, item). A winner is required, or `voided = true` (admin only, "item not played"); there are no ties. A base may only INSERT scores for its own matches, in round order and only after the arrival is confirmed (`validate_score`, 0022), and cannot edit afterwards; only the admin edits/deletes (every change goes to `score_audit`). Triggers maintain `matches.status` and `finished_at`; `team_standings` is a view that counts points.
- **Personal passports (0023–0025):** every inductor has a PERSONAL login (`public.passports`, NO row in `profiles`: it reads no group, base, match or score) that opens only their passport, which is the passport of THEIR WHOLE LIFE IN THE INDUCTION: the cover and the identity page (the DNI) are general (the mark of their career, photo, nickname, song, entry, generation: no theme, committee, role or partner), and every induction (a `terms` row: name like 2710 + theme + `welcome`) brings its own pages in its own theme. `passport_records` (one per person and term: role runner/base/coordinator, career, culture, `committee` + `committee_lead` (a coordinator of the committee: golden stamp; a committee may have several since 0026) and `extra_committees` + `extra_leads` (more committees, 0027), `team_id` (max 2 people per group) or `base_id`, same term as the Carrera), `term_committees` (the words of each committee in each induction) and `passport_stamps` (kept for ever: `archive_event_stamps()` runs in `events_archive_stamps`, which sorts BEFORE `events_reset_on_deactivate` and so archives before the reset). `my_passport_context()` / `my_live_stamps()` give the screen the names (and the photos of the group or base) and the finished matches of the running Carrera, nothing else. NOBODY edits their own passport row (0025 dropped the policy): the coordinator sets nickname, song, generation, entry, committee; the server changes the @ and the password in `api/account.ts` with the service role, asking the current password. The users API creates the login with `role: 'member'` and rolls it back if the row fails.
- **Schedule:** unique index on the unordered team pair (no repeated matchups per Carrera), a team plays once per round, a base hosts one match per round (`validate_match`, `unique(base_id, round_number)`).
- **Carrera states (0032):** `events.phase` is `disabled` → `enabled` (ready, buttons off, tutorial for bases and runners) → `started` (the time runs, bases act) → `finished` (locked, the coordinator validates); `is_active` always equals `phase <> 'disabled'` (a trigger keeps them equal; setting `is_active = true` means started). The coordinator moves it only through `event_action()` (`PhaseControl`): `disable` (from enabled or finished) archives and resets as before, `reset` (only from finished) clears the progress WITHOUT the history and goes back to `enabled`. A base acts (arrival, scores, alerts, rotation ack) only when `staff_can_act()`, i.e. started; reads and the coordinator are unaffected. `check_delays()` and `lateTeams` count the walk from the rotation notice of the previous round.
- **Staffing:** one inductor per base and one runner per team per Carrera (0003), one GPS tracker per team, min. 2 runners per team to activate. Activating a Carrera runs `event_problems()` (photos, info, 3 questions, runners…) — only one Carrera is active at a time.
- **Carreras and privacy (0014, 0019, 0020):** only one Carrera is active (`events_single_active`); only a deactivated one can be deleted (`events_delete_guard`); **deactivating resets its progress** (`reset_event_progress`: scores, audit, alerts, locations, arrivals; keeps teams, bases, users, schedule) but first saves a readable copy of the final table and every point in `event_archives` (0028, `events_archive_scores`; shown in `/admin/historial`). Carreras are deactivated, never deleted: they stay as the coordinator's history. Each runner/inductor belongs to ONE Carrera (`profiles.event_id`, `my_event_id()`) and reads only that Carrera's rows; **scores (and the `team_standings` view) are readable only by the admin, that base's inductor and the runners of that match** — phones never get other groups' points. A group needs at least 1 user (a pair may share one). Inductors act only on the ACTIVE Carrera (`is_staff_of_match`). `alerts.target` is `groups` or `base`, and since 0031 `alerts.team_id` (optional) sends a hurry alert to ONE group of the match (admin → base alerts ring the inductors; a base cannot target itself; 20 s limit per base).
- **Privacy:** a base's `info` and questions (at least 5, each with its `answer`, up to 10; `event_problems` requires them to activate a Carrera, 0030) are in `base_details` / `base_questions`, readable only by the admin and that base's inductors (0008). Runners get only name, photo and lat/lng of bases. `team_locations` (GPS) is readable only by the admin and, for its own row, the designated tracker.
- RLS helpers are SECURITY DEFINER functions (`is_admin()`, `is_staff_of_match()`, `is_staff_of_base()`); base arrival goes through the `confirm_arrival()` RPC instead of table writes.

### Personal passports
The catalog is kept in the database (0035) and edited from `/admin/comites` and `/admin/programas`: `committees`, `career_groups` + `careers`, `themes` (one is always the global one) + `theme_cultures` + `group_cultures`; `lib/catalog.ts` loads them at sign-in into `COMMITTEES` / `THEMES` (changed in place; `useCatalogVersion` redraws), and the built-in lists are the fallback. A passport can be an ancestor (`passports.status`, `disable_at`): it keeps opening until `disable_at`, then `passport_active()` hides it. One new inductor is added with the form in `/admin/inductores` (the Excel is only for bulk).

`/admin/inductores` (`Inductores.tsx`, global view) is the ONLY place where people are registered, and it opens on the list («Todos los inductores»: `matchesSearch` — each typed word must START a word of the name, nickname, career, generation or @ —, `FilterChips` that add up inside a group and narrow down between groups, `lib/inductors.ts`): `NewInductorForm` registers one (name, CAREER chosen from the catalog, a required GENERATION with a button to Generaciones, nickname and a song searched and listened to right there) and `InductorsBulk` does many (`templateWorkbook`, `parseInductors` of `lib/inductors.ts`, a default generation for rows without one, a card per person where the career and generation are fixed, the songs searched in Apple Music and listened to by the coordi before saving, and an Excel with the @ and passwords at the end; people already registered only get a song); both create the login only through `createInductor` (the one caller of `createPassportUser`, which undoes the login if the data is refused) and name everyone with `passportUsername` (first name + first surname, unique). The person's career lives in `passports.career` (0043; read apart like the song so the list opens before it is applied) and joins a carrera with it; `joined_term` is never typed: the generation brings it (`entryOf`, plus a trigger). `PersonEditor` («Editar perfil» in each row) edits name, career, generation, nickname, song and photo with one save. The per-carrera Excel is gone (inside a carrera people only join it, and the words of the induction stay there): the culture of a career comes from the theme of THAT carrera when the person joins it (`lib/themes.ts`: Sistemas→nórdica, Mecatrónica/Redes/Electrónica→griega, Industrial→mexicana, Bioingeniería/Mecánica→china, Civil→egipcia; unknown careers are chosen by hand; a theme the app does not know gets neutral pages with its own name). The GENERATIONS are a global, permanent catalog (`generations`, 0039, edited in `/admin/generaciones`): each has the seal the app brings and, once edited, its own shape/colour/picture (`GENERATIONS` in `lib/seals.ts`, changed in place by `setGenerations` from `loadCatalog`; `GenerationSeals` draws either). A person's `passports.generation` is CHOSEN from it (`GenerationPicker`; a trigger rejects names not in the catalog and saves the exact names, « / »-joined for two generations) — never typed. `/pasaporte` (`MemberHome` → `MemberPage` → `MemberPassport`) is the same booklet for everyone (no role versions, no control tower): identity page with the `Insignia` of the career (the medal of the Javeriana, `Insignia.tsx`: gold, eight arms, ribbon in the colours of the flag, blue enamel with the illustration of the approved draft per career, drawn as vectors in an 800 box (`InsigniaEmblems.tsx`); a career the app does not know keeps the old `CareerPlate`); tapping it opens it in the zoom of the stamps with the text of the career (`InsigniaStory`, `lib/insigniaTexts.ts`), the generation seal (`GenerationSeals`: Peluches, Barbies, Champiñones, Textiles) and the entry, then per induction (newest first) the induction page (name, theme, coordinators' words, culture `CultureSeal` made of a drawing of the culture's PLACE, never the gods/creatures of the base stamps), one committee page for EACH committee of the person (`committeesOfRecord`: the main one plus `extra_committees` since 0027; `CommitteeSeal`, golden when they coordinate it; six committees, Bienvenida and Meraki have a silhouette of their own via `ShapeSeal`; the committee's words; the golden `PhotoSeal` with the photo of the runner's group or the base inductor's base) and the visa pages (empty ones always wait), then blank pages. The SONG of each person (`passports.song`, 0042: a 30 s preview from the public Apple Music/iTunes search, validated by a trigger; the old personal symbol is gone, its columns unused) is chosen by the coordinator in the global Inductores (`SongCell`, in the registration form and the profile editor, or in the bulk Excel: a form with a song column is searched at a gap of 3.2 s because the catalogue limits ~20 searches a minute, and the coordinator listens to every proposal before applying it) and plays in the passport (`SongPlayer`, one app-wide audio in `lib/songPlayer.ts`; it starts when the cover is tapped; the volume slider is hidden where the phone ignores it). `MemberProfile` (second tab) changes the @/password and downloads the PDF (`lib/passportPdf.ts`: the same pages as SVG from the same components → canvas JPEG → `lib/pdf.ts`; fixed light colours; its chunks are out of the service-worker precache). `auth.tsx` turns a login without profile into a synthetic `member` role by reading `passports`. The app keeps working before 0024/0025 are applied (queries retry without the new columns).

### Roles and routing
The admin panel has THREE levels (0036): `/admin` = all the carreras (code, state, the permanent test carrera, history; "Nueva carrera" calls `create_event()`, which gives the next code 2710 → 2730 → 2810…), `/admin/carreras/<id>/…` = everything that belongs to ONE carrera (`CarreraShell`: configuracion, grupos, bases, cruces, usuarios, puntajes, mapa; the open carrera comes from the address, `useAdmin().event`), and the global pages (`inductores`, `programas`, `comites`, `insignias`, `sellos`, `historial`). **Nothing is entered or controlled twice:** the carrera state (`PhaseControl`) only in Resumen y control (`EnVivo`); seals are created and edited ONLY in the workshop (global `/admin/sellos`: `Sellos.tsx` + `SealEditor`), each made FOR a section (generation, theme, subtheme, group, base, committee) and, except generations (global, table `generations`), for ONE carrera — the database (0040, `event_seals_valid_ref`) refuses a seal for an element of another carrera and drops it with its element; the sections of a carrera (`SectionSeals`, in Temática, Bases, Coordi y comités; groups have NO seals, their insignia represents them: 0041) only SHOW their own seals, read only, with a link to the workshop; a static test guards all of it. **The side menu shows ONE level at a time** (`AdminNav`): inside a carrera there is NO global administration; the carrera menu is Resumen y control + Preparación (8 numbered steps in the order they are done) + En carrera (Puntajes, Radar), folded by phase (`groupOpenIn`); `CarreraShell` has no bar of tabs (a thin strip on phones). Resumen y control is the checklist (`PrepSteps`, `usePrepStatus`) while the carrera is being prepared and the tower once it runs; Configuración holds only settings. Carreras are never deleted: the states are disabled → enabled → started → finished → archived (Finalizada, history with all its data; `reopen` goes back). The old `/admin/grupos`-style paths redirect (`LegacyRedirect`). Inside a carrera (0037): `tematica` (its OWN theme: `themes.term_id`, copied from a template by `create_event(p_theme)`), the seals of the carrera (`event_seals`: unique design per kind; the coordi gets the golden seal from a trigger; edited in the workshop, no tab here), `inductores` (`Inductores fixedTermId` = the records of the carrera's semester; it only ADDS an existing person to the carrera or removes them from it (`onJoin`/`onLeave`) — a person is created ONLY in the global Inductores (`NewInductorForm` / `InductorsBulk`), and identity/password/ancestor controls exist only there, `view='global'`), `comites` (`event_committees` + `events.coordinator_id` + the committee coordis by `committee_lead`).

`App.tsx` routes `/admin/*` (nested pages inside `AdminLayout`, which provides the `useAdmin()` context: current Carrera, `selectEvent`, `reload`), `/base` and `/corredor`, each wrapped in `RequireRole`. The role comes from `public.profiles`. Login is username + password; `src/lib/username.ts` maps `username` → synthetic email `username@carreapp.test` (never change that domain; typing the full email also works). Users are created/reset/deleted only through `api/users.ts` (service-role key, admin-only). The admin panel has two modes (`AdminLayout` keeps `mode`, follows whether a Carrera is running): **En carrera** (`/admin` = En vivo, Puntajes, Mapa — nothing to create) and **Preparación** (`/admin/carrera` opens with the ordered steps; Grupos, Bases, Usuarios, Cruces — the schedule is hand-made, there is no generator); `docs/wiki/Pantallas.md` records where each piece of information lives and why — update it when moving things.

### Tests
`tests/db/` runs every migration unmodified in in-memory Postgres (PGlite) over Supabase stand-ins (`harness.ts`, `seed.ts`; roles via `asUser`/`asAnon`). `tests/db/race.test.ts` simulates a full Carrera. `tests/static/` parses the client code against the real schema (contract), design rules and docs (every migration must have a `## NNNN — ` section in `Registro-SQL.md`; every env var in `.env.example`). `tests/db/simulacro.test.ts` replays the whole test Carrera (`public/plantillas/carrera-de-prueba.xlsx`) end to end. `TEST_MUTATION_SQL` injects SQL after the migrations to prove a rule's tests fail when it is broken. A new rule → a migration + a test + a Registro-SQL entry. The `carreapp-tester` agent (`.claude/agents/`, tracked in git) runs all of it, invents extra cases, reviews screens and writes `docs/wiki/Informe-de-pruebas.md`.

### Data flow on the client
Pages query Supabase directly with PostgREST embedded selects (e.g. `matches(… bases(…), match_scores(…))`), filtering "my team/base in the active Carrera" with `!inner` embeds. Live updates go through `useRealtimeReload(tables, load)` (`src/lib/realtime.ts`): Realtime events + 20 s polling + refresh on focus/online, because iOS suspends sockets when the phone locks. Tables used with it must be in the `supabase_realtime` publication. One-to-one embeds (`base_details`) may arrive as an object or an array — use `infoOf()`.

### Delay alerts (computed twice — keep both in sync)
A group is "late" when its previous match finished more than the allowed minutes ago and the base has not confirmed arrival for the next one. The allowed time is per leg (`base_travel_times`, from-base → to-base) with `events.max_travel_minutes` as fallback.
- Client: `src/lib/delays.ts` (`lateTeams`) drives the banners and the in-app sound (`src/lib/alerts.ts`, repeats every 30 s; iOS audio needs a tap to unlock).
- Server: `check_delays()` (pg_cron every 30 s, scheduled by `supabase/push_setup.sql`) → `push_send()` → `net.http_post` to `api/push.ts` (secret header) → `web-push` → `src/sw.ts` (custom service worker, `injectManifest`). Only **runners** get sound/push; the admin and bases *send* alerts (`alerts` table; `alerts_push` trigger).
- Delay-related thresholds are duplicated in `lateTeams` and `check_delays()`.

### Other pieces worth knowing
- **Maps:** Mapbox GL is lazy-loaded (`LazyMap` → `MapView`) and excluded from the service-worker precache. The token is URL-restricted, so basemap tiles do not load on localhost (markers still do).
- **Photos:** Supabase Storage bucket `photos`; images are resized to 1000 px in the browser before upload, plus a 240 px copy (`-s.jpg`, `thumbPath`) that avatars, crests and lists use through `PhotoImg` (it falls back to the big one for older photos); `deletePhoto(s)` removes both (`src/lib/image.ts`, `storage.ts`).
- **Backup and keep-alive:** `npx tsx --env-file=.env.local scripts/backup.ts` copies every table, the logins (id and @ only) and all photos to `../carreapp-respaldos/` (outside the repo: personal data; a test makes it cover every table the migrations create). `api/keepalive.ts` + the daily cron in `vercel.json` keep the free Supabase project from being paused after a week without activity.
- **Bulk upload:** `src/lib/bulk.ts` is a pure parser/validator (Word via `mammoth` → HTML tables, Excel via `read-excel-file`, CSV); tables are recognised by their column titles and every section is optional. `pages/admin/BulkImport.tsx` executes it; templates live in `public/plantillas/`.
- **Design system ("Visado": an international trip, two experiences — runners are travellers with a passport, the coordinator operates a control tower):** all colours are CSS variables in `src/index.css` (`:root` = dark "passport by night", `:root[data-theme='light']` = the paper, which is the DEFAULT theme; both must define the same variables; text pairs are contrast-tested). Gold foil (`--foil`), stamp inks (`--ink-1..5`). **Stamps** (`Stamp.tsx`, `lib/seals.ts`, `InkSeals.tsx`): each base prints one of fifteen mythology seals (a picture already turned into ink: `public/sellos/ink/*.png` is white where there is ink and transparent elsewhere — the original pictures are NOT in the repository — used as a mask by `InkPicture` so it takes the colour of the stamp; outside the service-worker precache), assigned without repeats by the base's position in the Carrera's list (`registerSealRoster` / `sealForSeed`; the colour is fixed per mythology, `CULTURE_INK`); the silhouette (hexagon, shield, arch…), ink and tilt come from the id so it looks the same for runner, base and admin, and the name goes on a band under the drawing; a stamp is earned when the match is finished (the base scored the three stages: barra, pregunta, minijuego); the airport vocabulary (group = flight `JV 2xx`, base = destination with a 3-letter code, gate = round) is derived from real data in `lib/flight.ts` and never stored. The coordinator panel is `.admin.tower` (layer 6 of `index.css`, "Centro de control"): it follows the light / dark switch like the runner and the base, with no palette of its own — the navy desk (side menu; a floating pill on phones), boarding-pass tickets (`CarreraTicket`, the carreras list, the gates of the round, the strip of indicators), a navy departure board (`FlightBoard`), gold foil and the paper pattern behind; modules Flight board / Gates / Passport matrix (Puntajes) / Operations log (`OpsLog`) / Radar (Mapa). Headings have NO kicker above them: Preparación screens carry a `StepTag` ("Paso n de 8", `PageTitle`). Page turns use View Transitions (`lib/motion.ts`). No emojis (Lucide icons, `Crest`/`Avatar` show initials without a photo). Theme in `src/lib/theme.ts` (`ThemeToggle`, saved in localStorage). Logo: the crest (`Logo.tsx`, masks from `public/crest-simple.svg` + `wordmark.svg`; gold crest on the passport cover; app icons without text; sources in `docs/logo/final/`, see Diseno.md). **Pop-ups never use `window.confirm/prompt`**: use `confirmDialog` / `promptDialog` (`src/lib/dialog.ts`, drawn by `DialogHost`). Suggested passwords are silly leet-speak words plus four random digits (`src/lib/password.ts`; the runners' @ is visible to the other runners, so the digits keep the public word lists from being enough to guess one). See `docs/wiki/Diseno.md`.
- **Phone screens by role:** runner = Visado (destination card with the three stages) / (Ubicación only for the designated GPS user: fixed, non-interactive map) / Pasaporte (cover shown every time the tab opens, opens on tap, identity page with route map, stamp pages) / Top (own points + every team by name only); base = Ronda (stages are played and scored minijuego → pregunta → barra; after a match is scored the "Equipos en rotación" card waits for the coordinator's rotation notice (`round_rotations`, 0029) and the base confirms it let the groups go (`rotation_acks`); navy "visa counter" ticket + one thing at a time on the Ronda tab (groups walking with a clock and hurry buttons per group → stages to score → only the rotation button → next match), groups as passengers with flight codes, tinted with the base's own stamp ink `--base-ink`; same account sheet (the sound and notification switches live there, between the theme and sign out; no bell in the bar), folder tabs, floating nav and tab slide as the runner) / Resultados (teams by photo+name, no points; history of what it scored with the winner of each item) / Mi base (guide, questions, photo, location; the map only opens to change it). `NoActiveCarrera` is the empty state. Top bars use `AccountMenu` (avatar + name + @user; light/dark and sign out).
- **Notifications:** `src/sw.ts` closes previous notifications and shows each push with a unique tag (so every alert rings); in-app alerts (`useManualAlerts`) show only the newest, ring at once, and remember dismissed ids in localStorage so a reload does not bring them back.
- **Server clock:** delay alerts use `serverNow()` (`src/lib/clock.ts`, `server_now()` RPC), not the phone clock.

## Conventions that are easy to miss

- **Migrations:** never edit an applied script — add the next `00NN_name.sql` and a row + section in `docs/wiki/Registro-SQL.md` (what changes, why, verification, how to revert). The user applies it by hand, so when pushing code that depends on a new migration, say so: the deploy lands in ~15 s and the app breaks until the SQL runs. If the SQL Editor reports permission/RLS errors, the session role was changed: run `reset role;` first.
- **Commits:** conventional messages (`feat(db):`, `feat:`, `fix:`, `docs(wiki):`, `chore:`), several focused commits per change, and **never add a Co-Authored-By or any attribution line**. Do not commit or push until the user asks.
- **Resume point:** read `docs/wiki/Estado-y-pendientes.md` first (current state, pending list, conventions, environment traps).
- **Third-party skills** (`.claude/skills/`, `.claude/agents/impeccable-*`) are installed but gitignored.
- **Docs:** after each block of work update `docs/wiki/` (`Bitacora.md`, `Registro-SQL.md`, `Home.md` status, and `Roles-y-permisos.md` / `Modelo-de-datos.md` / `Diseno.md` when relevant). The GitHub wiki is published by copying `docs/wiki/*.md` into a clone of `https://github.com/zdan13l/CarreApp.wiki.git` (branch `master`) and pushing. `README.md`'s roadmap is stale; the wiki is the source of truth.
- Developed on Windows with Git Bash: `.gitattributes` forces LF, so CRLF warnings on `git add` are expected.
